## 🔴 Critical Issues (Ảnh hưởng trực tiếp đến hiệu năng)

### 1. Đồng bộ hóa I/O tập tin trên Thread chính (Blocking Main Event Loop)
- **Vị trí:** `src/planScanner.ts`, `src/extension.ts`, `src/sidebarProvider.ts`, `src/bridgeServer.ts`
- **Triệu chứng & Hậu quả:** Sử dụng các hàm đồng bộ `fs.existsSync`, `fs.readdirSync`, `fs.readFileSync`, `fs.statSync` liên tục trong quá trình quét thư mục kế hoạch (`scanPlanFolder`), phát hiện workspace (`discoverWorkspacePlanFolders`), và ghi registry (`registerPortInRegistry`). Khi thư mục có nhiều file, VS Code bị khựng UI (giao diện đơ vài giây).
- **Cách khắc phục:** Chuyển sang dùng `fs.promises` (bất đồng bộ async/await) hoặc `vscode.workspace.findFiles` của VS Code API.

### 2. Gửi tin nhắn IPC Webview dồn dập không Throttled (`logUpdate` & `stateUpdate`)
- **Vị trí:** `src/sidebarProvider.ts:137-147`, `src/extension.ts:1099`
- **Triệu chứng & Hậu quả:** Mỗi dòng log mới từ `transcriptWatcher` lập tức gọi `postMessage` sang Webview. Khi AI tạo transcript liên tục với hàng chục dòng/giây, hàng nghìn tin nhắn IPC dồn về Webview làm Webview Sidebar giật lag và CPU bị quá tải.
- **Cách khắc phục:** Áp dụng kĩ thuật **Debounce / Throttle** (ví dụ gom log đẩy theo chu kỳ 100ms - 200ms) để giảm tần suất IPC `postMessage`.

### 3. Quét DOM `querySelectorAll('*')` quy mô lớn trên toàn bộ VS Code Workbench
- **Vị trí:** `media/autoplan-dom-bridge.js:28-53`, `media/autoplan-dom-bridge.js:361-390`
- **Triệu chứng & Hậu quả:** Hàm `queryDeep` duyệt tất cả các phần tử `*` của DOM kể cả trong Shadow DOM. Khi tính năng Auto-Approval chạy mỗi 1 giây (hoặc mỗi Mutation event), việc duyệt qua hàng chục nghìn element của VS Code Electron làm ngốn lượng lớn CPU của Renderer Process, làm quạt máy tính kêu to và giật lag ứng dụng.
- **Cách khắc phục:** Giới hạn phạm vi tìm kiếm (Scoping) chỉ trong khung Chat Container (`.interactive-session`) hoặc dùng CSS selector cụ thể thay vì `querySelectorAll('*')`.

### 4. Vòng lặp Polling Timer song song với Native File System Watcher
- **Vị trí:** `src/transcriptWatcher.ts:484-514`, `src/transcriptWatcher.ts:644`
- **Triệu chứng & Hậu quả:** Vừa sử dụng `fs.watch` vừa bật `setInterval(..., 300ms)` liên tục đọc đĩa. Polling 300ms quá dày đặc kể cả khi không có file thay đổi gây lãng phí tài nguyên CPU và pin laptop.
- **Cách khắc phục:** Tăng khoảng thời gian Polling (ví dụ 1000ms) làm phương án dự phòng khi `fs.watch` không hoạt động, hoặc sử dụng Adaptive Backoff (kéo dài thời gian poll khi rảnh).

## 🟡 Warnings (Nên tối ưu bộ nhớ & CPU)

### 1. Phình to DOM trong Webview Sidebar khi Transcript dài (`sidebar.js`)
- **Vị trí:** `media/sidebar/sidebar.js`
- **Triệu chứng & Hậu quả:** Mặc dù phía Extension Host giới hạn 100 dòng log, nhưng phía Webview HTML (`#transcript-log`) liên tục `appendChild` mà không dọn dẹp các dòng log cũ trong DOM tree.
- **Cách khắc phục:** Thêm cơ chế Pruning / Virtual Scroll trong `sidebar.js` (chỉ giữ tối đa 100-200 DOM element trong thẻ log).

### 2. Tách mảng String không cần thiết khi kiểm tra trạng thái Phase
- **Vị trí:** `src/planScanner.ts:107`
- **Triệu chứng & Hậu quả:** `detectPhaseStatus` đọc toàn bộ file và gọi `.split(/\r?\n/)` tạo ra mảng hàng nghìn string trong RAM chỉ để đọc 30 dòng đầu.
- **Cách khắc phục:** Đọc file dưới dạng stream hoặc chỉ slice phần đầu (ví dụ 4KB đầu tiên) để regex match.

### 3. Định dạng Tooltip Status Bar liên tục 1 giây/lần
- **Vị trí:** `src/extension.ts:329-352`
- **Triệu chứng & Hậu quả:** Timer `setInterval` 1000ms chạy liên tục tạo ra chuỗi Markdown Tooltip mới ngay cả khi người dùng không rê chuột vào status bar.
- **Cách khắc phục:** Chỉ cập nhật Tooltip khi trạng thái Phase thực sự thay đổi hoặc dùng định dạng nhẹ hơn.
